# 排水底图厘米→分米保流向转换（Flask + SQLite）

## 1. 背景

旧排水程序只读取**整数分米**高程，对厘米测量值逐格取整。缓坡上相邻两格的厘米高差
可能只有 3–7 cm，取整后被压成同一分米值，原本的下坡变成平地、流向丢失或凭空新增，
且无法处理并列最低与坑点（无下坡）。

本服务接收**整数厘米高程 CSV**（≤ 32×32 格）与**最大允许误差 E（厘米）**，
求解一份**整数分米 CSV**，保证：

1. 每格 `|10·D[r,c] − H[r,c]| ≤ E`；
2. 转换前后每格流向完全一致；
3. 关键格（如沟口）可锁定分米值，测绘更正上传时沿用锁定重新求解；
4. 误差限内无解时不覆盖上一份可下载底图，并给出**最小可行误差**；
   放宽误差仍无解时，明确报告锁定值与流向不可兼得。

### 流向定义（严格按需求）

> 每格的流向 = 四邻（上/下/左/右，不含对角）中**最低且严格低于本格**的**所有**邻格。

* 多个邻格并列最低 → 全部保留（多流向）；
* 没有严格更低的邻格 → 流向为空（坑点/无下坡），转换后仍须为空。

## 2. 算法

把所有要求写成整数差分约束 `D[v] − D[u] ≤ w`：

| 要求 | 约束 |
|---|---|
| 每格误差 ≤ E | 每格绝对取值区间 `[⌈(H−E)/10⌉, ⌊(H+E)/10⌋]`；锁定格区间收缩为单值 |
| H 的下坡邻格 v（H[v]<H[u]）保持下坡 | `D[v] ≤ D[u] − 1`（边 u→v，权 −1） |
| 等高/更高邻格不得变成下坡 | `D[v] ≥ D[u]`（边 v→u，权 0） |
| 并列最低邻格之间 | 分米值相等（两条 0 权边） |
| 最低邻格 vs 其他下坡邻格 | 最低者严格更低（权 −1 边） |

* 以上界为 SPFA 初始距离（隐式 0 权超级源），求逐点最大解并检测负环；
* 出现负环，或最大解仍低于某格下界 → 该 E 下不可行；
* 对 E 二分得到**最小可行误差**（上界取一个必然容纳全部排序需求的大值，
  若大误差仍无解，则判定为锁定与流向的硬冲突）；
* 每个成功解在返回前都会再次做完整自检（误差、锁定、逐格流向集合相等）。

实现见 `app/solver.py`，32×32 随机底图完整转换（含二分）实测约 0.4 s。

## 3. 数据与保留语义（SQLite）

* `projects`：转换任务（固定行列尺寸）；
* `locks`：分米锁定值（沟口等），更正与重转时自动沿用；
* `snapshots`：每次转换尝试。成功存分米格网与逐格误差；失败只存状态
  （`tight` 误差过紧 / `conflict` 硬冲突），`grid_dm` 为 NULL；
* `checks`：双路来水核查。绑定一份成功快照，保存两个来水格、一个沟口格、
  冻结的厘米底图、备选高程测段，以及建立时一次算好的全部测段取值组合
  （压缩流向与双路结果）；
* `check_confirmations`：核查内每个测段的确认取值（快照值/备选值）。

**可下载底图永远取最新一条 `status='ok'` 的快照**：失败尝试（包括失败的测绘更正）
不会覆盖它，锁定值也不会被清除。

## 4. 双路来水核查

养护员可在一份**转换成功（`status='ok'`）的快照**上核查：两处来水能否各走一条支路，
汇进同一个沟口。

1. 在底图页「双路来水核查」表单中选定快照，指定**来水甲、来水乙、沟口**三个格子
   （均用 1 基行列，三格不能重合）。
2. 上传**备选高程 CSV**，每行 `测段,行号,列号,备选厘米值`（首行表头可省略）：
   * 最多 **8** 个测段；同一格只能填写一次（跨测段重复也拒绝）；
   * 每个测段二选一：整段统一用**快照厘米值**，或整段统一用**备选厘米值**；
   * 未列入任何测段的格子（包括关键格）始终使用快照厘米值。
3. 两条路线必须在**同一套**测段取值下沿现有四邻流向到达沟口，且**只在沟口相交**。
   求解为节点拆点后求两条点不相交路径（每格容量 1，沟口容量 2）。
4. 网页列出**一套成立的测段选择**与两条**逐格路线**（含每格采用后的厘米值和所属测段），
   并给出核查格网与流向图。没有任何一套取值可行时，明确提示「找不到双路」。
5. 复测后可对**每个测段**逐段确认「用快照值/用备选值」，也可**撤销确认**（恢复按建议取值）。
   确认与撤销只读取建立核查时一次算好的全部取值组合的流向与路线，不重新转换、不重算流向；
   保存失败时提示失败，页面仍显示此前的确认与结果。
6. 核查冻结所用快照的厘米底图（`checks.input_cm`）：之后上传的测绘更正只新增快照，
   **不改变这次核查所用的快照**与结果。

确认数据存于 `check_confirmations`，核查与预计算结果存于 `checks`，均在 SQLite 中，
重启后继续可查、可确认。

## 6. 启动

### Docker Compose（推荐）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

SQLite 数据库持久化在宿主 `app/local_data/drainage.db`，容器重建不丢数据。
健康检查：`GET /healthz`。

### 本地直接运行（无 Docker 时）

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python -m app.serve          # 工作目录为仓库根；默认 0.0.0.0:8000
```

### 测试

```bash
python -m unittest discover -s tests -v
```

## 7. 网页演示路径（用 sample/ 数据）

1. 首页新建任务，上传 `sample/slope_cm.csv`，误差填 **9** → 转换成功，
   页面并列出厘米/分米格网与流向箭头（`·` 为无下坡，多箭头为并列）；
   该底图最小可行误差为 7 cm。
2. 误差改填 **0** 重转 → 提示“最小可行误差为 7 cm”，下载按钮给出的仍是旧底图。
3. 锁定沟口（第 6 行第 6 列 = 8 dm）后重转 → 锁定格高亮 `L`，值被严格遵守。
4. 上传 `sample/correction_cm.csv`（同尺寸测绘更正）→ 沿用锁定转换成功。
5. 制造硬冲突：把 (6,6) 锁 17、(6,5) 锁 16（与原高低关系颠倒），
   即使误差放到 100000 也提示“锁定值与流向要求无法同时满足”。
6. “下载当前分米 CSV”得到整数分米结果；转换历史保留全部尝试与状态。

### 双路来水核查演示

1. 在底图页「双路来水核查」中选择快照 **#1**（slope_cm.csv 的初次转换），
   来水甲 **1 行 1 列**、来水乙 **1 行 6 列**、沟口 **6 行 6 列**。
2. 上传 `sample/check_alternatives.csv`（7 段；其中「甲腰」备选值 300 会把
   甲路从经过 (3,3)→(3,4) 改道到 (4,2)→(4,3)）→ 页面给出一套成立的测段选择与两条逐格路线：
   * 来水甲：11 格，(1,1)…(6,6)；
   * 来水乙：6 格，(1,6)…(6,6)；
   * 两路只在沟口 (6,6) 相交。
3. 点「确认用备选值」确认「甲腰」→ 页面列出甲路改为经过 (4,2)、(4,3)，
   结果 pill 显示「甲腰·备」；点「撤销确认」→ 恢复原路线。
4. 再上传一次测绘更正，刷新核查页：路线、取值与快照 #1 均不变。
5. 把来水甲改成 6 行 1 列、来水乙 6 行 6 列、沟口 1 行 1 列（逆流）→ 提示「找不到双路」。

## 8. 已验证的关键行为（自测，56 项测试全过）

* CSV 校验：非整数、缺列、空文件、超过 32×32 均被拒绝；
* 流向：并列最低全保留、无下坡保持为空、对角格不参与；
* 任意可行解逐格误差 ≤ E、锁定值精确满足、转换前后流向集合逐格相等；
* 0 误差仅在全 10 倍数且排序兼容时可行，否则给出最小可行误差；
* 随机 30 组底图 + 32×32 满尺寸底图不变量成立；负高程可解；
* 误差过紧：失败提示最小误差，上一份成功底图与锁定原样保留；
* 硬冲突：任意放宽误差均无解并明确提示；
* 测绘更正：尺寸不符被拒；失败更正只新增失败记录，不改变可下载底图。
* 双路核查：备选 CSV 4 列/整数/1 基/每格唯一/最多 8 段均校验；三格重合被拒；
  只接受转换成功的快照；关键格可不列入测段（按快照值参与）；
  两条路线逐跳都在已算流向上、只在沟口相交；
  随机底图上双路结果从不出现沟口外交叉；
  逐段确认/撤销后页面路线按已确认值变化（甲腰备选值使甲路改道），重启后确认仍在；
  保存失败时提示失败且保留此前确认；后续测绘更正不改变核查所用快照与结果；
  无合规组合时提示「找不到双路」。

## 9. 限制与未完成事项

* 本环境未安装 Docker 守护进程，镜像构建与 `docker compose` 未做真机验证，
  仅对容器内将运行的同一入口（`python -m app.serve` + waitress）做了本地实测；
  Dockerfile/compose 语法已人工核对。
* SPFA 对 32×32（≤1024 节点）实测足够快；双路核查会预计算最多 2⁸=256 套
  测段取值（各算一次流向与两条点不相交路径），32×32 满尺寸 8 段实测约 3 s，
  属建立核查时的一次性成本；确认/撤销只读缓存。
* 双路核查要求同尺寸快照；未列入备选高程 CSV 的格子一律使用快照厘米值，
  因此若想让某格参与「测段统一取值」，必须把它写进对应测段。
* 无用户体系，任务对所有访问者可见；SECRET_KEY 走环境变量，生产部署需覆盖默认值。
* CSV 仅支持 UTF-8（含 BOM）整数文本，未支持浮点/空格分隔等变体。
